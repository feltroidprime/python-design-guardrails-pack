# SPEC-0001 — Recursive Proof-Carrying Repository

- Status: proposed
- Schema version: 1
- Scope: this repository and every capability it generates
- Replaces: the single example application recorded in ADR-0001, superseded
  by ADR-0007
- Owners: repository maintainers
- Revisit trigger: a further stage of this specification lands, or the
  shipped ownership model diverges from what is written here
- Primary principle:

> The repository uses hexagonal architecture, an agent-native CLI, and an
> executable proof system to generate new units that use the same
> architecture, CLI contracts, and proof system.

This is the repository's own copy of its generation specification. ADR-0007
records why the repository adopted it and which decision it replaces. This
copy is the one that evolves: later work implements it section by section,
and each landing keeps this document, not a private plan, as the normative
target. A section describing behavior not yet built still states a MUST —
it is the contract that work must satisfy when it lands, not a report of
what already exists.

---

## 1. Objective

A freshly generated repository MUST be a valid, useful repository without
containing an arbitrary example domain.

The repository MUST start as an N0 capable of generating its own N1, N2, N3,
and subsequent product capabilities.

The permanent code delivered by the template MUST progressively become a
smaller proportion of the repository without requiring the user to delete or
rewrite template example code.

The repository MUST support all application shapes through composition of
capabilities, rather than through one global application-type choice.

Examples include, without being limited to:

- pure Python libraries;
- local or remote CLIs;
- HTTP services;
- workers and scheduled jobs;
- stateful workflows;
- data pipelines;
- GitHub, MCP, subprocess, filesystem, database, or network integrations;
- multi-agent orchestrators.

The template MUST NOT assume that the product needs:

- a database;
- a repository abstraction;
- an event bus;
- generated identifiers;
- a clock;
- a runtime CLI;
- async execution;
- a web framework;
- CRUD operations.

Those capabilities are introduced only when the product requires them.

---

## 2. Non-goals

The repository generator MUST NOT become:

- a runtime plugin framework;
- a dependency-injection container;
- a business-domain DSL;
- a generic repository framework;
- a generic entity hierarchy;
- a framework that dynamically discovers product modules at runtime;
- an automatic business-logic generator.

The generator creates architectural boundaries, ownership declarations,
activation points, and proof obligations.

It MUST NOT invent product semantics.

---

## 3. Definitions

### 3.1 N0

N0 is the freshly generated repository.

N0 contains:

- the repository control plane;
- architecture and dependency guards;
- the executable proof system;
- the agent-native repository CLI;
- the product package foundation;
- empty generated indexes;
- no product capability.

N0 contains no `Item`, `Task`, `Order`, `Resource`, `Record`, or equivalent
placeholder domain.

### 3.2 Capability

A capability is the smallest independently owned vertical product unit.

It is simultaneously:

- an architectural unit;
- an ownership unit;
- a proof unit;
- a composition unit;
- an activation unit;
- a retirement unit.

A capability internally follows hexagonal dependency direction:

```text
domain ← application ← adapters ← bootstrap
```

### 3.3 System capability

A system capability belongs to the repository control plane rather than the
product.

The initial system capability is:

```text
repository-generation
```

It plans and applies new product capabilities.

It MUST satisfy the same structural, proof, and CLI contracts as product
capabilities. It MUST NOT receive architecture exceptions merely because it
is the generator.

### 3.4 Product capability

A product capability belongs entirely to the repository user.

Examples might eventually be:

```text
billing
workflow_execution
market_data
video_processing
github_automation
```

These names are supplied by the user. None ships with N0.

### 3.5 Foundation

Foundation code is maintained by the template and may evolve through
scaffold updates.

### 3.6 Product code

Product code is created for the user and becomes user-owned immediately.

Neither the generator nor a future scaffold update may overwrite product
code.

### 3.7 Derived code

Derived code is a deterministic projection of declarations and product
manifests.

Derived code is always replaceable and MUST never be edited manually.

## 5. Ownership model

Every repository path belongs to exactly one ownership class.

The classes MUST be disjoint.

### 5.1 FOUNDATION

Examples:

```text
repoctl/**
src/<package>/_foundation/**
scripts/**
.github/**
root configuration files
proof/policy.toml
tests/foundation/**
tests/repoctl/**
verification/repoctl/**
```

Properties:

- maintained by the template;
- updated through Copier or a future versioned migration;
- updates use three-way merge where files may have local edits;
- foundation files MUST NOT contain product-domain concepts.

### 5.2 PRODUCT

Examples:

```text
src/<package>/modules/**
proof/modules/**
tests/modules/**
verification/modules/**
docs/product/**
```

Properties:

- owned by the user immediately after creation;
- never overwritten by capability generation;
- never overwritten by scaffold updates;
- never rewritten by a blueprint upgrade;
- never deleted by `retire`;
- absent from the Copier template except for an optional ignored placeholder
  that contains no code.

A file initially seeded by the generator becomes PRODUCT as soon as it
exists.

There is no continuing generator ownership of seed files.

### 5.3 DERIVED

Examples:

```text
src/<package>/_generated/**
proof/_generated/**
docs/architecture/generated/**
```

Properties:

- deterministic;
- reproducible from repository declarations;
- safe to overwrite;
- contains a generated banner and source-state digest;
- never imported by a product module;
- imported only by composition roots or foundation entry points.

### 5.4 DECLARATION

Examples:

```text
.repo/repository.toml
.repo/capabilities/*.toml
```

Properties:

- machine-readable and versioned;
- modified only through compare-and-swap semantics;
- may be inspected by humans and agents;
- MUST NOT contain business rules;
- MUST NOT embed executable Python;
- MUST preserve unknown future-compatible fields or reject an unsupported
  schema version.

### 5.5 Ownership invariant

For every write operation:

```text
write(path) implies
    path belongs to DERIVED
    or
    path is an absent PRODUCT seed target
    or
    path is a DECLARATION with the expected previous digest
    or
    path belongs to an explicit FOUNDATION update transaction
```

No operation may write an existing PRODUCT file.

## 6. The capability contract

Every system or product capability MUST satisfy the same contract.

### 6.1 Required structure

A capability MUST have:

```text
api.py
domain/
application/
adapters/inbound/
adapters/outbound/
```

`bootstrap.py` is required only when the capability owns runtime
composition.

Empty packages are allowed while the capability is in `draft` state.

The generator MUST NOT create fake entities, fake use cases, fake
repositories, or `NotImplementedError` business methods.

### 6.2 Dependency direction

Inside one capability:

```text
domain:
    may depend on standard library and icontract only

application:
    may depend on its own domain

adapters:
    may depend on its own application and domain

bootstrap:
    may depend on every layer of its own capability
```

A capability MUST NOT import another capability's internals.

Allowed cross-capability interactions are:

1. import from the other capability's `api.py`;
2. inject an application-owned port;
3. consume an explicitly published stable event;
4. compose both capabilities in the outer bootstrap.

The preferred interaction is a consumer-owned port injected by the
composition root.

### 6.3 Public surface

`api.py` is the only stable import surface of a capability.

Other capabilities MUST NOT import:

```text
modules.<name>.domain.*
modules.<name>.application.*
modules.<name>.adapters.*
modules.<name>.bootstrap
```

The architecture guard MUST enforce this.

### 6.4 No shared product abstractions by default

The repository MUST reject or require an ADR for introduction of:

```text
BaseEntity
BaseRepository
GenericRepository
Service
Manager
common/
shared/
utils/
helpers/
```

A shared product abstraction is admitted only after at least two concrete
capabilities demonstrate the same stable requirement.

## 7. Capability declaration

Each capability has one declaration:

```toml
schema_version = 1
name = "billing"
python_module = "acme.modules.billing"
status = "draft"
proof_catalog = "proof/modules/billing.toml"

[boundaries]
inbound = ["python"]
outbound = []

[activation]
api = "acme.modules.billing.api"
factory = ""
cli_catalog = ""
```

### 7.1 Field semantics

`name`:

- lowercase snake case;
- globally unique;
- maps exactly to the directory name.

`python_module`:

- MUST equal `<package>.modules.<name>`;
- cannot point outside the configured product root.

`status`:

```text
draft
active
retired
```

`boundaries.inbound` and `boundaries.outbound`:

- document architectural seams;
- are identifiers, not framework selections;
- do not generate business behavior;
- MAY cause creation of empty adapter packages;
- MUST be checked against actual activation declarations where
  mechanically possible.

`activation.api`:

- points to the stable product-facing facade.

`activation.factory`:

- optional composition factory;
- required when the capability owns runtime-wired dependencies.

`activation.cli_catalog`:

- optional agent-native product command catalog;
- required only when the capability exposes product CLI commands.

## 8. Capability lifecycle

The normative state machine is:

```text
ABSENT
  └── apply(valid_plan) ──► DRAFT

DRAFT
  ├── activate(valid_evidence) ──► ACTIVE
  └── retire ────────────────────► RETIRED

ACTIVE
  └── retire ────────────────────► RETIRED

RETIRED
  └── activate(valid_evidence) ──► ACTIVE
```

Deletion is intentionally absent from schema version 1.

Retirement removes runtime exposure but preserves all product code.

A future destructive `purge` operation requires a separate specification,
preview, explicit confirmation, and protection of modified files.

### 8.1 DRAFT

A draft capability:

- exists in product code;
- is included in architecture and proof discovery;
- is excluded from runtime composition;
- is excluded from the product CLI catalog;
- may contain no public behavior yet;
- MUST satisfy proof closure for any public behavior it does contain.

### 8.2 ACTIVE

An active capability:

- is present in the derived active-capability index;
- may be wired into runtime composition;
- may contribute commands to the product CLI;
- has a non-empty stable surface or explicit inbound entry point;
- passes architecture, type, proof, and command-contract gates.

### 8.3 RETIRED

A retired capability:

- remains entirely user-owned;
- is absent from runtime and CLI derived indexes;
- is not deleted or rewritten;
- can be reactivated after satisfying current contracts.

## 9. Repository control-plane architecture

The `repository-generation` system capability MUST itself use the
capability contract.

Its core operation is:

```text
plan(repository_snapshot, capability_intent) -> capability_plan
```

This function is pure.

Effects belong to the application layer:

```text
apply(capability_plan, repository_port) -> apply_result
```

The local filesystem implementation belongs to the outbound adapter.

The CLI belongs to the inbound adapter.

No domain or application code may call:

```text
open
Path.write_*
os.*
subprocess.*
git
network APIs
environment variables
wall clock
randomness
UUID generation
```

Those effects are injected through ports when needed.

## 10. Capability intent

The user supplies structural intent, not business semantics.

Example:

```json
{
  "schema_version": 1,
  "name": "workflow_execution",
  "inbound": ["python", "cli"],
  "outbound": ["clock", "checkpoint_store", "agent_runner"]
}
```

The generator may use this information to create:

- capability directories;
- empty boundary packages;
- a capability declaration;
- an empty capability proof catalog;
- local agent instructions;
- empty test and verification directories.

It MUST NOT generate:

- a `Workflow` entity;
- transition semantics;
- retry policies;
- fake ports with guessed method names;
- adapter implementations;
- fake tests that always pass;
- fake properties.

The agent or user supplies product vocabulary and laws after scaffolding.

## 11. Capability plan

`plan` produces a versioned, deterministic, inspectable value:

```json
{
  "schema_version": 1,
  "plan_id": "sha256:...",
  "generator_version": "1.0.0",
  "base_state_digest": "sha256:...",
  "intent": {
    "name": "workflow_execution",
    "inbound": ["python", "cli"],
    "outbound": ["clock", "checkpoint_store", "agent_runner"]
  },
  "operations": [
    {
      "kind": "create_product_seed",
      "path": "src/acme/modules/workflow_execution/api.py",
      "precondition": "absent",
      "content_digest": "sha256:..."
    },
    {
      "kind": "update_declaration",
      "path": ".repo/capabilities/workflow_execution.toml",
      "precondition": "absent",
      "content_digest": "sha256:..."
    },
    {
      "kind": "write_derived",
      "path": "proof/_generated/index.json",
      "precondition_digest": "sha256:...",
      "content_digest": "sha256:..."
    }
  ],
  "result_state_digest": "sha256:..."
}
```

### 11.1 Plan invariants

For the same canonical snapshot, intent, and generator version:

```text
plan(snapshot, intent) == plan(snapshot, intent)
```

A plan MUST:

- contain every intended write;
- contain no hidden write;
- use normalized repository-relative paths;
- reject absolute paths;
- reject `..` path escape;
- classify every target by ownership;
- include preconditions for every operation;
- include its generator version;
- include a stable plan ID;
- be serializable to canonical JSON.

A plan MUST NOT depend on:

- current time;
- random values;
- filesystem enumeration order;
- locale;
- machine hostname;
- current user;
- network availability.

---

## 12. Plan application

Application is explicit:

```text
plan → inspect → apply
```

No planning command may modify the repository.

`apply` MUST:

1. verify the plan schema;
2. verify the generator version;
3. verify the plan ID;
4. verify the base-state digest;
5. verify every operation precondition;
6. reject any existing PRODUCT seed target;
7. write an operation journal;
8. stage all new content;
9. apply operations in deterministic order;
10. regenerate derived indexes;
11. verify the result-state digest;
12. mark the transaction complete.

A stale plan MUST fail with no silent replan.

The recovery action MUST be stated in the structured outcome:

```text
re-run capability plan against the current repository state
```

Applying the same successful plan again MUST return a stable no-op or
already-applied result. It MUST NOT duplicate files or declarations.

## 13. Derived compiler

The repository compiler reads declarations and emits explicit Python and
JSON indexes.

It MUST NOT perform runtime module discovery.

### 13.1 Runtime capability index

Generated from active capability declarations:

```python
ACTIVE_CAPABILITIES = (
    "acme.modules.billing",
    "acme.modules.workflow_execution",
)
```

### 13.2 Composition index

Imports only declared factories:

```python
from acme.modules.billing.bootstrap import build as build_billing
```

### 13.3 Product CLI index

Imports only capability-local command catalogs declared by active
capabilities.

### 13.4 Proof index

Aggregates system and product proof catalogs with exact ownership
metadata.

### 13.5 Derived exactness invariant

For every repository state:

```text
derived_active_capabilities
    == exactly the declarations whose status is ACTIVE
```

There may be no missing, duplicated, retired, or undeclared capability in a
derived index.

## 14. Agent-native CLI

The repository control CLI is always present.

The product CLI is optional and capability-driven.

### 14.1 Control-plane commands

Schema version 1 defines:

```text
repo capabilities
repo status

repo capability plan NAME
repo capability apply PLAN
repo capability activate NAME
repo capability retire NAME

repo generate
repo proof-report
```

Example:

```bash
uv run python -m repoctl capability plan workflow_execution \
  --inbound python \
  --inbound cli \
  --outbound clock \
  --outbound checkpoint_store \
  --outbound agent_runner \
  --output .repo/plans/workflow_execution.json

uv run python -m repoctl capability apply \
  .repo/plans/workflow_execution.json
```

### 14.2 Protocol requirements

Every command MUST:

- accept ordinary arguments;
- work without a TTY;
- never prompt during automation;
- use JSON as the default output;
- use stdout for successful data;
- use stderr for diagnostics;
- have versioned result envelopes;
- declare retry and safety semantics;
- expose recoverable outcomes and recovery guidance;
- have an independent detached-process contract case.

The control-plane CLI and any product CLI MUST satisfy the same behavioral
contract test kit, even if they do not share implementation code.

## 15. Proof-carrying capability contract

Every public behavior in a capability's configured proof surface MUST be
owned by a named property or a future-dated explicit exemption.

Property IDs are namespaced:

```text
REPOCTL::PLAN-DETERMINISTIC
BILLING::INVOICE-TOTAL-PRESERVED
WORKFLOW-EXECUTION::TERMINAL-RUN-CLOSED
```

Each normative property MUST declare:

```text
id
statement
scope
assumptions
targets
oracles
evidence
counterexample
failure_modes
```

### 15.1 Evidence mapping

Use:

- `icontract` for executable preconditions, postconditions, and invariants;
- Hypothesis for broad input spaces and metamorphic properties;
- Hypothesis `RuleBasedStateMachine` for history-dependent behavior;
- CrossHair for pure, deterministic, I/O-free functions;
- port contract tests for adapter implementations;
- process contract tests for CLI boundaries.

### 15.2 Activation proof rule

A capability cannot become ACTIVE unless:

- its architecture contract passes;
- its stable surface is non-empty;
- every public core behavior is classified;
- every normative property has canonical evidence;
- every pure contracted target required by policy is a CrossHair target;
- every declared port has a behavioral contract;
- every declared CLI command has independent process evidence;
- generated indexes are exact.

## 16. Normative properties of the repository generator

The `repository-generation` system capability replaces the arbitrary
example domain as the repository's permanent proof specimen.

At minimum, it owns these properties.

### REPOCTL::PLAN-DETERMINISTIC

```text
The same canonical state and intent produce the same plan and plan ID.
```

Evidence:

```text
icontract + Hypothesis + CrossHair
```

### REPOCTL::PLAN-PATH-CLOSED

```text
Every planned target is repository-relative and belongs to an allowed
ownership zone.
```

Evidence:

```text
icontract + Hypothesis + CrossHair
```

### REPOCTL::APPLY-IDEMPOTENT

```text
Applying an already successfully applied plan creates no additional
change.
```

Evidence:

```text
Hypothesis stateful
```

### REPOCTL::STALE-PLAN-REJECTED

```text
A plan whose preconditions no longer match is rejected without silently
overwriting current state.
```

Evidence:

```text
Hypothesis stateful + real filesystem contract
```

### REPOCTL::PRODUCT-BYTES-PRESERVED

```text
No plan, regeneration, activation, or retirement operation modifies an
existing PRODUCT file.
```

Evidence:

```text
Hypothesis stateful + filesystem contract + mutation canary
```

### REPOCTL::DERIVED-INDEX-EXACT

```text
Derived indexes contain exactly the capabilities represented by current
declarations.
```

Evidence:

```text
icontract + Hypothesis + CrossHair
```

### REPOCTL::ACTIVATION-CLOSED

```text
A capability cannot become active without its required architecture,
proof, composition, and CLI evidence.
```

Evidence:

```text
Hypothesis stateful
```

### REPOCTL::RETIREMENT-NON-DESTRUCTIVE

```text
Retirement removes exposure but preserves declarations and all product
files.
```

Evidence:

```text
Hypothesis stateful + real filesystem contract
```

### REPOCTL::INDEPENDENT-CAPABILITIES-COMMUTE

```text
For two non-conflicting intents A and B, applying A then replanning and
applying B produces the same canonical final state as applying B then
replanning and applying A.
```

Evidence:

```text
Hypothesis metamorphic property
```

These properties test the actual repository architecture rather than a toy
business domain.

## 17. Self-hosting requirement

The repository generator MUST be validated as a capability.

There MUST be one capability validator used for both:

```text
repoctl/modules/repository_generation
src/<package>/modules/<product-capability>
```

The validator may receive different root and ownership parameters, but
MUST NOT have weaker rules for `repoctl`.

The following must be identical for system and product capabilities:

- layer dependency rules;
- public-surface rules;
- proof-catalog schema;
- property/evidence closure;
- port-contract requirements;
- CLI contract requirements;
- module size and naming policies.

This is the recursive core:

```text
the generator is one valid capability
that generates other valid capabilities
that can coexist and generate further capabilities
through the same repository control plane
```

## 18. Testing strategy

Testing is organized in six independent layers.

### 18.1 Pure planner proofs

Target:

```text
plan(snapshot, intent) -> plan
compile_indexes(declarations) -> derived_state
classify_path(path) -> ownership
```

Test with:

- icontract;
- Hypothesis;
- CrossHair.

Generated cases include:

- valid and invalid names;
- Unicode and normalization boundaries;
- path traversal;
- path collisions;
- duplicate names;
- empty boundaries;
- unknown future manifest fields;
- unsupported schema versions;
- 0 to 100 existing capabilities.

### 18.2 Reference state machine

Build one independent `RuleBasedStateMachine` whose model contains only:

```text
capability status
declaration state
product file hashes
derived index membership
applied plan IDs
```

Rules include:

```text
plan capability
apply valid plan
apply same plan again
apply stale plan
manually modify product file
activate draft
attempt invalid activation
retire active
reactivate retired
regenerate indexes
add second capability
```

Global invariants:

```text
existing product bytes never change
active index equals active declarations
retired capabilities are absent from runtime indexes
successful plan IDs are not applied twice
no path exists outside allowed roots
declarations and generated indexes agree
```

Hypothesis must shrink failures to minimal action sequences.

### 18.3 Port contract tests

Define one reusable filesystem/repository contract.

Certify at least:

- an in-memory implementation;
- the real local filesystem implementation.

Contract cases include:

- absent-file creation;
- compare-and-swap success;
- compare-and-swap conflict;
- directory creation;
- normalized path handling;
- symlink escape rejection;
- interrupted transaction detection;
- journal recovery;
- read-after-write consistency.

### 18.4 CLI process contract

Invoke every repository command as a detached process with closed stdin.

Verify:

- default JSON;
- stable envelope;
- stdout/stderr separation;
- no prompt;
- unknown command;
- invalid schema;
- stale plan;
- path conflict;
- already-applied result;
- missing proof evidence;
- retirement;
- bounded `capabilities` query.

### 18.5 Recursive end-to-end acceptance

The pack test creates a fresh N0 repository and executes:

```text
1. render N0
2. bootstrap N0
3. validate repository-generation as a system capability
4. run repo capabilities
5. plan capability alpha
6. apply capability alpha
7. assert alpha contains no invented business logic
8. add a minimal real alpha implementation from a test fixture
9. add alpha properties and evidence
10. activate alpha
11. run prove-one for alpha
12. run the full gate
13. plan and apply capability beta from the resulting N1 repository
14. verify alpha's product bytes are unchanged
15. activate beta
16. retire alpha
17. verify alpha's files remain unchanged
18. verify derived runtime indexes contain beta but not alpha
19. run the full gate again
```

This proves:

```text
template → N0
N0 → N1
N1 → N2
N2 can change composition without rewriting N1 product code
```

### 18.6 Application-shape matrix

Product fixtures are test-only and are never delivered in N0.

The matrix contains:

#### Pure library capability

Tests:

- no application effects;
- no adapters required;
- CrossHair operates on pure functions;
- stable `api.py` export.

#### Stateful workflow capability

Tests:

- explicit state transitions;
- retry and cancellation sequences;
- Hypothesis state machine;
- clock and execution ports.

#### CLI capability

Tests:

- capability-local command catalog;
- generated global catalog;
- process cases;
- activation and retirement.

#### External integration capability

Tests:

- application-owned port;
- fake adapter;
- real adapter contract;
- translated failures.

#### Multi-capability composition

Tests:

- capability A consumes a port;
- capability B satisfies it through its public API;
- global bootstrap injects B into A;
- A imports no B internals.

Every matrix member is created through the real repository CLI.

## 19. Mutation testing requirements

The test suite MUST catch temporary mutations equivalent to:

1. planner emits an absolute path;
2. planner emits `../`;
3. apply overwrites an existing PRODUCT file;
4. apply ignores a stale digest;
5. apply duplicates one declaration;
6. derived compiler omits an active capability;
7. derived compiler includes a retired capability;
8. activation ignores missing proof evidence;
9. retirement deletes product code;
10. identical intents produce different plan IDs;
11. capability A imports capability B internals;
12. a CLI command exists without an independent process case;
13. an oracle returns `True`;
14. a pure target is removed from CrossHair coverage.

Temporary mutations are removed after validation.

The suite records which deterministic mechanism catches each mutation.

## 20. Future scaffold-update compatibility

Full product migration tooling is deferred, but schema version 1 MUST make
it possible without redesign.

The following constraints apply immediately.

### 20.1 Product roots are absent from the Copier template

Copier updates MUST have no template-owned file under:

```text
src/<package>/modules/**
proof/modules/**
tests/modules/**
verification/modules/**
```

Therefore a normal scaffold update cannot overwrite product code.

### 20.2 Generated outputs have isolated roots

All safely replaceable files live under a `_generated` directory.

A future migration may regenerate them without inspecting product
behavior.

### 20.3 Manifests are versioned

Both repository and capability declarations include:

```text
schema_version
```

Future schema migrations are expressed as:

```text
migrate(snapshot) -> migration_plan
```

The migration planner is pure and uses the same plan/apply protocol.

### 20.4 No blueprint replay

The generator may seed product files once.

A later template version MUST NOT reapply a newer blueprint over an
existing capability.

The capability records the generator version for provenance only.

It does not transfer future ownership to the template.

### 20.5 Update-preservation acceptance test

Even before update commands are implemented, pack CI MUST simulate:

```text
1. render repository with foundation version A
2. create one capability
3. modify every seeded product file
4. apply a synthetic foundation version B update
5. regenerate derived indexes
6. compare product file hashes before and after
```

The required result is byte-for-byte equality for every PRODUCT file.

### 20.6 Reserved future protocol

The following command names and semantics are reserved:

```text
repo update plan
repo update apply
repo update status
repo update recover
```

They MUST eventually use the same inspectable plan, compare-and-swap,
ownership, journal, and recovery model as capability generation.

No separate mutation mechanism may be introduced for updates.

## 21. Performance requirements

After one warm run on the reference repository:

```text
repo status:
    median < 250 ms with 100 capabilities

repo capability plan:
    median < 500 ms with 100 capabilities

repo generate:
    median < 1 s with 100 capabilities

repo capability apply:
    median < 1 s for one empty capability capsule

just prove-one:
    interactive target, preferably < 5 s

just prove:
    daily target, preferably < 10 s
```

No planning, generation, activation, or proof-closure operation may
require network access.

Deep symbolic or stateful exploration remains a separate command.

## 22. Definition of done

This specification is fully realized when:

- N0 contains no arbitrary product domain;
- repository-generation is a valid proof-carrying hexagonal capability;
- the control CLI is agent-native and fully contract-tested;
- capability planning is pure and deterministic;
- capability application is explicit, journaled, and compare-and-swap
  safe;
- existing product files are never overwritten;
- active composition is derived from declarations;
- runtime discovery is absent;
- draft, active, and retired states are mechanically enforced;
- the repository proves N0 → N1 → N2 end to end;
- every application-shape fixture in the testing strategy passes;
- future scaffold updates can be introduced without changing the
  ownership model;
- product code is outside every template-owned update path.

The central invariant is:

> Foundation may evolve, derived code may be regenerated, declarations may
> be migrated through explicit plans, but product code is written once and
> then belongs exclusively to the user.
